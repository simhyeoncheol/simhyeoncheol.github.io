차곡 (Chagok)

공부 시간을 재고, 공부하는 동안 방해되는 앱과 사이트를 막아 주는 공부 스톱워치입니다.

AndroidiOSWebmacOSWindowsChrome 확장

차곡 · 공부 스톱워치, 앱·사이트 차단

React Native 앱(공부 타이머, 월간 통계, 주간 그래프)

iOS(Screen Time 권한, 허용 앱 선택, 공부 중 앱 차단)

Android(권한 안내, 접근성 서비스로 앱 차단)

Windows 데스크톱 앱(C#, WebView2)

Chrome 확장(차단 페이지, 허용 목록 팝업)

프로젝트 소개

여러 기기에서 이어지는 공부 스톱워치로, 세션 중에는 OS별로 방해 앱과 사이트를 차단합니다. 웹, 모바일, 데스크톱, 브라우저 확장이 단일 Supabase 백엔드와 TypeScript 공용 패키지(도메인, 동기화, 차단 규칙)를 공유하는 pnpm 모노레포 구조입니다.

주요 구현 기능

01

멱등 오프라인 동기화

Outbox 패턴으로 모든 명령을 로컬(IndexedDB / SQLite)에 먼저 기록하고 commandId 기반으로 재전송해 서버에서 멱등하게 처리합니다. 동시 수정은 expectedVersion 기반 낙관적 동시성 제어로 감지하고 server-wins로 해소합니다.

02

플랫폼 독립 차단 엔진 계약

BlockEngine 계약을 iOS(FamilyControls), Android(접근성 서비스 / Device Owner), macOS 에이전트, Windows, Chrome 확장(MV3)이 각각 구현합니다. 정책 버전·만료·권한 상태 판정은 공용 decideApply가, 서버 지시 적용과 상태 보고는 BlockCoordinator가 담당합니다.

03

타임존·DST 인지 통계

이벤트 구간만 저장하고 자정 경계에서 날짜별로 분할, 겹치는 구간은 합집합으로 계산합니다. 서버 집계(daily_stats)와 클라이언트 계산 결과를 Asia/Seoul, America/New_York 기준으로 교차 검증했습니다. 클라이언트 시각은 RTT 최소 표본 기반 서버 오프셋으로 보정합니다.

기술적 과제와 해결

iOS Screen Time 차단의 자가 만료 설계

과제공부 세션이 끝나면 앱 프로세스 생존 여부와 무관하게 기기에서 차단이 해제돼야 했습니다.

분석앱이 해제를 직접 수행하면 앱이 종료된 경우 차단이 남기 때문에, 실패 시 차단이 남지 않는 fail-safe 원칙을 세우고 OS 스케줄러(DeviceActivity)에 만료를 위임했습니다. 다만 DeviceActivity는 15분 미만 구간을 거부하고(intervalTooShort) 최대 1주로 제한되며, 앱 토큰이 50개를 넘으면 차단이 전혀 적용되지 않는다는 개발자 포럼 보고가 있었습니다.

해결잔여 시간이 15분 미만이면 16분 구간을 등록하고 warningTime을 실제 만료 시각에 맞춰 경고 콜백에서 해제하며, intervalDidEnd는 예비 해제로 둡니다. 시작 시각은 내림, 만료 시각은 올림해 조기 해제를 막았습니다. 만료 예약이 실패하면 방금 적용한 Shield를 즉시 롤백하고, 토큰은 50개에서 잘라 partial 상태로 보고합니다.

성과15분 경계, 자정 경계, 1주 초과 케이스를 포함한 단위 테스트 21개를 작성했습니다. 시뮬레이터에서 정책 만료 후 차단 해제를 확인했고 실기기 검증은 진행할 예정입니다.

Android 차단: 접근성 서비스와 Device Owner 이중 구현

과제Android에서 세션 중 지정 앱의 사용을 차단해야 했습니다.

분석일반 앱 권한인 접근성 서비스는 앱 실행 후 화면을 가리는 사후 차단이라 타이밍 경쟁이 있습니다. GLOBAL_ACTION_HOME이 비동기로 늦게 적용돼 차단 화면을 덮는 현상을 로그 타임스탬프(차단 화면 24.715s, HOME 24.868s)로 확인했습니다. Device Owner의 setPackagesSuspended는 실행 전 차단이 가능하지만 공장 초기화 기기에서만 프로비저닝할 수 있습니다.

해결권한 수준별로 두 엔진을 구현하고 공통 BlockEngine 계약 뒤에 두었습니다. 접근성 엔진은 차단 Activity를 먼저 띄우고 HOME은 실패 시 fallback으로만 쓰며, 같은 패키지의 창 이벤트는 700ms 디바운스합니다. Device Owner 엔진은 대상만 suspend하고 isPackageSuspended로 OS 상태를 재조회해 active / partial / failed를 판정합니다. 기본 SMS 앱과 현재 IME는 안전 예외로 두고, 재부팅 후에도 suspend가 유지되므로 BOOT_COMPLETED와 알람에서 만료를 재검사합니다.

성과에뮬레이터(API 36)에서 15개 시나리오, JVM 단위 테스트 11개 통과. Device Owner 모드는 suspend, 재부팅 후 유지, 해제를 검증했습니다.

macOS 차단 에이전트의 집행 검증

과제macOS에서 세션 중 지정 앱이 실행되면 종료해야 했습니다.

분석NSRunningApplication.terminate()의 반환값은 요청 전달 여부일 뿐 실제 종료를 보장하지 않고, 샌드박스에서는 false를 반환해 Mac App Store 배포로는 집행이 불가능했습니다. LSUIElement 앱은 실행 알림이 오지 않습니다. 검증 중 집행된 것처럼 보인 케이스도 통합 로그 분석 결과 대상 앱의 자체 종료로 확인돼, 성공 판정 기준을 API 반환값이 아닌 프로세스 상태로 정의했습니다.

해결kill(pid, 0)과 isTerminated로 프로세스 소멸을 확인한 경우에만 집행 성공으로 집계하고, 5초 내 미종료는 partial로 보고합니다. 알림 누락은 1초 주기 스캔으로 보완하고, heartbeat가 5초 이상 끊기면 agent_unreachable로 보고합니다. 정책은 state.json에 영속화해 재시작 시 복원하며, 배포 채널은 Developer ID 직접 배포로 결정했습니다.

성과종료 확인 233~1972ms, 만료 후 해제 8ms. 허용 목록 시험 전후 비대상 프로세스 95개 PID 불변을 확인했고 swift test 33개가 통과했습니다.

다중 기기 세션의 동시성 제어와 멱등 처리

과제같은 계정으로 여러 기기에서 세션을 시작·종료하고, 오프라인 중 쌓인 명령은 재연결 시 재전송합니다.

분석두 기기의 동시 START는 애플리케이션 레벨 check-then-insert로는 경쟁 조건을 막을 수 없어 활성 세션이 2개 생길 수 있습니다. 재전송 구조상 같은 명령이 여러 번 도착하므로 서버 처리가 멱등해야 했습니다.

해결RPC 안에서 profiles 행을 SELECT … FOR UPDATE로 잠가 직렬화하고, 활성 세션에 부분 유니크 인덱스를 걸었습니다. 클라이언트는 명령을 outbox에 먼저 기록한 뒤 commandId(PK)와 함께 재전송해 서버에서 멱등하게 처리되고, 상태 변경은 expectedVersion 기반 낙관적 동시성 제어로 충돌을 감지합니다.

성과실제 PostgreSQL 17 동시 연결 테스트에서 START 12건 → 활성 세션 1건, 동일 commandId 8건 → 이벤트 1건을 확인했습니다.

Chrome MV3 확장의 fail-safe 만료

과제사이트 차단은 Chrome 확장이 네이티브 메시징 호스트(차곡 앱)에서 정책을 받아 적용합니다.

분석호스트 프로세스가 종료되거나 연결이 끊겨도 차단이 무기한 남으면 안 됐습니다. MV3 서비스 워커는 수명이 짧고, 규칙 적용이 이미 열린 탭에는 반영되지 않으며, 등록 API 호출 성공이 실제 규칙 반영을 보장하지 않았습니다.

해결chrome.alarms 30초 주기로 동기화하고, 호스트에 연결되지 않으면 캐시된 정책을 expiresAt까지만 유지한 뒤 만료 알람으로 규칙을 제거합니다. 정책 변경 시 열린 탭을 차단 페이지로 전환하고, 적용 후 getDynamicRules()로 등록된 규칙 수를 재조회해 기대값과 일치할 때만 active로 보고합니다.

성과Chrome for Testing, Edge에서 차단·허용 목록, 열린 탭 전환, 호스트 단절 상태의 자가 만료를 검증했습니다.

네이티브 셸로 데스크톱 클라이언트 경량화

과제웹 클라이언트를 macOS와 Windows 데스크톱 앱으로도 배포해야 했습니다.

분석Electron은 웹 코드를 그대로 재사용할 수 있지만 번들 크기가 200MB를 넘었습니다.

해결macOS는 Swift + WKWebView, Windows는 C# + WebView2로 얇은 네이티브 셸을 만들고, 웹과 네이티브 기능 사이를 window.chagokDesktop 브리지 계약으로 연결해 웹 코드를 그대로 재사용했습니다.

성과번들 크기 macOS 약 2.2MB, Windows 약 4.2MB.
