CASE 01더바디채널 ERPJava · Spring · MyBatis · MySQL · PortOne

결제사 응답과 내부 결제 상태가 어긋나지 않게

결제 상태 불일치 지점 문의 해소 운영 중 지점 문의 기준

문제

PortOne 웹훅이 누락되거나 순서가 뒤바뀌어 도착했습니다. 취소 뒤 결제 완료 웹훅이 늦게 오면 이미 취소된 결제가 다시 완료로 바뀌었고, 취소 결과와 내부 환불 기록이 어긋나는 경우도 있었습니다. 일괄결제 웹훅에서는 상품 발급과 매출 반영이 빠졌습니다.

판단

웹훅이 언제 몇 번 오는지는 PG사가 정합니다. 받는 쪽이 중복, 순서 뒤바뀜, 누락을 모두 견뎌야 한다고 보고 웹훅을 결제 상태의 근거가 아닌 확인 신호로만 쓰기로 했습니다.

구현
  • 웹훅 수신 시 PortOne 결제 조회 API로 실제 상태를 다시 확인
  • 결제 ID 기준 처리 이력으로 같은 웹훅 중복 처리 차단
  • 취소 → 완료 같은 상태 역행을 막는 전이 검사
  • 미완료 결제를 주기적으로 조회해 누락된 웹훅 보정
  • 푸시 알림 같은 후처리 예외를 본 처리와 분리해 환불 기록이 롤백되지 않게 처리
결과

결제 상태가 맞지 않는다는 지점 문의가 더 이상 들어오지 않았습니다. 같은 맥락으로 0원 결제와 유효기간 변경, 양도에 GM 승인 절차와 사전 검증을 추가했습니다.

CASE 02이원헬스케어 통계 개선 프로젝트MSSQL · Oracle · 실행 계획

월별 진료 통계 40초를 1.78초로

40s → 1.78s, 약 22배 같은 조건의 월별 진료 통계 조회 1회

문제

월별 진료 통계 하나를 띄우는 데 40초가 걸려 통계팀이 화면을 켜 두고 기다렸습니다.

판단

실행 계획에서 Table Scan과 Key Lookup 비용이 큰 구간부터 봤습니다. 기본키가 WHERE 조건에 없어 전체 스캔을 하고 있었고, 스칼라 함수와 조건절 함수 때문에 인덱스를 타지 못했습니다. 진료, 처방, 수납 같은 큰 테이블을 한 번에 조인하면서 실행 계획도 틀어져 있었습니다.

구현
  • 키 기준으로 조건 수정, 필요한 인덱스 추가
  • 조건절과 SELECT 절의 함수 제거
  • 기간으로 먼저 줄인 중간 결과를 임시 테이블에 담고 인덱스를 건 뒤 조인
결과

40초에서 1.78초로 줄었습니다. 같은 방식으로 퇴원심사 조회도 손봤는데, 행마다 호출되던 스칼라 함수와 함수 조건절을 걷어내 프로시저 3개를 고쳤고 프로시저당 13초에서 약 3초가 됐습니다.

CASE 03인천기독병원Oracle → MSSQL

운영 중인 병원 DB를 Oracle에서 MSSQL로 옮기기

진료 중단 없이 전환 야간 이관 후 건수·금액 대사

문제

진료가 멈추면 안 되는 병원에서 DB를 바꿔야 했습니다. 프로시저 10개 정도를 MSSQL로 옮기면서 NVL, DECODE, 시퀀스, 날짜 함수를 바꿔야 했습니다.

판단

문법만 바꿔서는 결과가 같다는 보장이 없다고 봤습니다. 전환 테스트에서 건수가 맞지 않는 쿼리가 나왔고, 원인은 Oracle이 빈 문자열을 NULL로 보고 MSSQL은 그렇지 않다는 차이였습니다.

구현
  • 빈 문자열과 NULL을 다루는 조건을 프로시저마다 다시 확인해 수정
  • 야간에 이관한 뒤 주요 테이블의 건수와 금액 합계를 양쪽 DB에서 비교
결과

진료 중단 없이 전환했습니다. 레거시 로직을 새 환경으로 옮길 때는 같은 입력에 같은 결과가 나오는지 숫자로 맞춰 보는 단계를 빼지 않습니다.

CASE 04사이드 프로젝트 차곡 (1인 개발)PostgreSQL 17 · Supabase · TypeScript

여러 기기가 동시에 요청해도 결과가 하나로

동시 시작 12건 → 활성 세션 1건 실제 PostgreSQL 동시 연결 테스트

문제

같은 계정으로 두 기기가 동시에 공부 세션을 시작하면 활성 세션이 두 개 생길 수 있었습니다. 오프라인에서 쌓인 명령은 재연결 때 다시 보내므로 같은 명령이 여러 번 도착합니다.

판단

애플리케이션에서 조회한 뒤 저장하는 방식으로는 경쟁 조건을 막을 수 없습니다. 직렬화와 중복 제거를 DB 트랜잭션과 제약 조건에 맡기기로 했습니다.

구현
  • 트랜잭션 안에서 사용자 행을 SELECT … FOR UPDATE로 잠가 직렬화
  • 활성 세션에 부분 유니크 인덱스
  • 명령을 outbox에 먼저 기록하고 commandId(PK)로 재전송해 서버에서 멱등 처리
  • expectedVersion 기반 낙관적 동시성 제어로 수정 충돌 감지
결과

동시 시작 12건에 활성 세션 1건, 같은 commandId 8건에 이벤트 1건이 남았습니다. Vitest와 PGlite로 권한 경계와 동시성까지 약 200개 테스트를 작성했습니다.

CASE 05이원헬스케어MSSQL · DMV · Oracle Listener

오전마다 멈추던 수납 화면과 DB 장애

오전 수납 멈춤 문의 해소 장애 원인 특정 후 재발 기준

문제

외래가 몰리는 오전에 여러 병원에서 수납 화면이 멈춘다는 전화가 동시에 왔습니다.

판단

DMV로 블로킹 세션과 원인 프로시저를 특정했습니다. 처방 저장과 수납 처리가 같은 테이블들을 서로 다른 순서로 갱신해 데드락이 났고, 인덱스 없는 조회가 락을 오래 잡고 있었습니다.

구현
  • 두 처리의 테이블 갱신 순서 통일
  • 트랜잭션 안의 불필요한 조회를 밖으로 이동, 인덱스 추가
  • 반복 지연은 인덱스 REBUILD와 통계 갱신으로 대응
결과

오전 수납 멈춤 문의가 사라졌습니다. 응급실 NEDIS 연동 DB 연결 장애는 Oracle Listener를 점검한 뒤 서버 디스크 부족으로 원인을 찾아 당일 복구했습니다.
