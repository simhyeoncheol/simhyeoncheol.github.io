러닝, 웨이트, 요가, 등산 등 11개 종목을 기록하는 운동 앱입니다. 종목이 달라도 하나의 Activity 모델로 저장합니다. iPhone(React Native)과 Apple Watch(SwiftUI) 중 어느 쪽에서 시작해도 세션 상태가 실시간으로 미러링되고, 기록은 단일 세션으로 저장됩니다.

주요 구현 기능

01

iPhone ↔ Watch 세션 미러링

WCSession을 래핑한 Expo 네이티브 모듈로 sendMessage(저지연)와 transferUserInfo(at-least-once)를 이중 전송하고 id 기반으로 중복 제거합니다. JS 리스너 등록 전 수신분은 네이티브 큐에 버퍼링합니다.

02

오프라인 우선 동기화

로컬 저장 → 동기화 큐 → Firestore 순의 오프라인 우선 파이프라인으로, 워치 기록도 같은 경로를 탑니다. 계정 이전은 멱등하게 처리하고 삭제는 tombstone으로 전파합니다. 응원 1인 1회 제한 같은 비즈니스 규칙은 Firestore 보안 규칙으로 강제합니다.

03

GPS 측정 엔진

종목별 이상치 필터, 히스테리시스 기반 자동 일시정지, MET 기반 칼로리, 1km split, 투 포인터 슬라이딩 윈도 기반 1K/5K/10K 최고 기록 계산을 순수 함수로 구현해 단위 테스트합니다.

기술적 과제와 해결

iPhone ↔ Apple Watch 실시간 상태 동기화

과제어느 기기에서 운동을 시작하든 두 기기가 같은 세션 상태를 실시간으로 표시해야 했습니다. 기존 라이브러리(react-native-watch-connectivity)는 수신 이벤트를 JS 레이어로 전달하지 않아 네이티브 브리지를 직접 구현했습니다.

분석WatchConnectivity는 채널마다 전달 보장이 다릅니다. sendMessage는 저지연이지만 상대가 reachable일 때만 전달되고, transferUserInfo는 큐 기반 at-least-once 전달, applicationContext는 last-write-wins로 마지막 값만 유지됩니다. 단일 채널로는 지연과 유실 중 하나를 감수해야 했고, 수신 시각 기준 보정은 기기 간 클럭 스큐와 전송 지연이 그대로 반영돼 경과 시간이 최대 5초 벌어졌습니다.

해결WCSession을 래핑한 Expo 네이티브 모듈을 작성해 같은 payload를 sendMessage와 transferUserInfo로 이중 전송하고 id 기반으로 중복 제거했습니다. JS 리스너 등록 전 수신분은 네이티브 큐에 버퍼링합니다. context는 이전 상태에 patch를 병합해 단일 dictionary로 전송하고, 경과 시간은 송신 측 측정 시각(measuredAt) 기준으로 양쪽에서 동일하게 보정합니다. 일시정지 중에도 heartbeat를 보내고, 35초 staleness 기준과 watchdog으로 세션 생존 여부를 판정합니다.

성과시뮬레이터 동시 캡처 기준 폰 0:41 / 워치 0:41로 일치했습니다. 미러링 중 값 이중 합산, stale context 오인 등을 회귀 테스트로 고정했습니다.

다른 기기 세션에 워치 센서만 제공

과제폰에서 시작한 운동에서도 페어링된 Apple Watch의 심박 센서를 사용해야 했습니다.

분석워치에서 HKWorkoutSession을 열어야 센서가 활성화되지만, 세션을 저장하면 HealthKit에 운동이 중복 기록됩니다. 두 기기가 거리·시간까지 모두 송신하면 어느 값이 원본인지(source of truth) 모호해지는 문제도 있었습니다.

해결"한 세션의 소유 기기는 하나"라는 원칙으로 역할을 분리했습니다. 워치에 sensingForPhone 모드를 두어 UI는 폰 세션을 미러링하고, HealthKit 세션은 센서 용도로만 열어 폰에 없는 지표(심박, 케이던스)만 5초 주기로 송신합니다. 종료 시 builder.discardWorkout()으로 저장하지 않아 HealthKit 중복을 막고, 집계는 마지막 값이 아니라 평균을 쓰며 미측정 구간(0)은 제외합니다.

성과케이던스 집계 로직은 단위 테스트로 검증했습니다. HealthKit 중복 방지는 실기기 검증을 진행할 예정입니다.

측정 엔진 감사(audit)와 재설계

과제기록 정확도가 서비스의 핵심이라 측정 파이프라인 전체를 항목별로 감사하고 문서화했습니다. 벽시계 기반 경과 시간, 누적 지표 처리 방식, 워치·HealthKit 간 거리 불일치가 주요 리스크로 확인됐습니다.

분석HealthKit 통계는 누적값으로 들어오기 때문에 수신할 때마다 더하면 이중 가산(0, 10, 20, 20, 35 → 85)이 발생하고, 값이 일시적으로 역행(100 → 98 → 101)할 때 증가분만 더해도 과대 집계(103)가 됩니다. Date.now() 차이로 계산한 시간은 기기 시계 변경에 영향을 받습니다. 계산 방식을 바로 교체하면 기존 기록과 수치가 달라지므로 비교 검증 단계가 필요했습니다.

해결누적값을 출처별 최신 관측으로 대체하고 표시값은 high-water mark로 단조 증가시키는 CumulativeLedger를 TypeScript와 Swift에 동일 규칙으로 구현했습니다. 시간은 단조 시계(performance.now(), 워치는 builder.elapsedTime)로, 평균 심박은 시간 가중 평균으로 전환했습니다. 신규 거리 추정기는 섀도 모드로 붙여 사용자 기록에 영향 없이 결과만 비교하고, 저장된 세션을 재실행하는 리플레이 CLI를 만들었습니다.

성과Jest 213 → 303 tests(26 suites), Swift 테스트 8개 통과, Release 빌드 성공(2026-09-29 기준). 실외 필드 테스트는 진행할 예정입니다.

Firestore 보안 규칙 기반 피드 접근 제어

과제별도 API 서버 없이 Firestore 보안 규칙만으로 피드 공개 범위(public / friends / private)를 강제해야 했습니다.

분석Firestore 규칙은 결과를 거르는 필터가 아니라 쿼리 단위로 평가됩니다. 목록 쿼리는 규칙상 읽을 수 없는 문서가 결과에 포함될 수 없음을 쿼리 조건으로 증명해야 통과하므로, 단건 get은 허용되고 list 쿼리만 permission-denied가 나는 형태로 드러납니다. 규칙 단위가 아니라 클라이언트가 실제로 보내는 쿼리 형태로 검증해야 했습니다.

해결피드와 Signal 쿼리에 visibility 제약을 추가하고, 앱의 쿼리 형태를 그대로 재현하는 규칙 에뮬레이터 테스트로 제약을 빼면 거부되는 것까지 고정했습니다. 초대 링크는 get과 list 권한을 분리해 링크(문서 id)를 아는 사용자만 단건 조회할 수 있고 목록에는 노출되지 않게 했습니다.

성과보안 규칙 테스트 36개를 작성하고 두 계정 간 팔로우 → 피드 노출 흐름을 검증했습니다.

오프라인 우선 구조의 계정 이전과 삭제 전파

과제비로그인 상태의 로컬 기록을 로그인 후 서버 계정으로 이전하고, 오프라인 우선 구조에서 삭제한 기록이 재동기화로 되살아나지 않게 해야 했습니다.

분석로그인 직후 동기화와 포그라운드 복귀 동기화가 겹치면 같은 작업이 동시에 실행되는 경쟁 조건이 생깁니다. 동기화 큐에는 이전 계정 소유로 남은 항목이 있었고, 경로 하위 문서는 부모 문서의 작성자로 권한을 판정하기 때문에 삭제 순서에 의존성이 있었습니다. 오프라인에서는 Firestore SDK promise가 resolve되지 않는 경우도 있었습니다.

해결로컬 이전 → 원격 pull → 큐 flush를 single-flight로 실행되는 syncAccount()로 묶고, 이전은 동일 id를 덮어쓰지 않는 멱등 연산으로 구현했습니다. 큐 항목의 소유자를 새 계정으로 재지정하고, 삭제는 tombstone(최근 200건)을 두어 업로드 전후와 워치 수신 시점에 검사합니다. 하위 문서부터 삭제하도록 순서를 고정하고, SDK 호출에는 10초 타임아웃을 두었습니다.

성과멱등 이전, 타 계정 데이터 비침범 등 계정 동기화 테스트 5개를 작성했습니다.

종목별 GPS 이상치 필터

과제러닝, 걷기, 등산, 사이클을 단일 GPS 측정 엔진으로 처리합니다.

분석단일 속도 임계값(12m/s)으로 이상치를 거르면 고속 종목의 정상 구간까지 제거됩니다. GPX 리플레이 테스트에서 3.07km 사이클 코스가 1.39km로 집계됐습니다.

해결종목별 속도 임계값(러닝 8, 걷기·등산 4, 사이클 25 m/s)으로 필터를 분리했습니다.
